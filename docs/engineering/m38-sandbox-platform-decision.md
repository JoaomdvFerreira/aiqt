# M38-WU01: Sandbox Platform Decision

## Decision

**Initial supported platform: Linux, via an OCI-compatible container runtime (`oci-container@1`).** Windows and macOS are **unsupported initially** and fail closed to the M37 request/import fallback. This decision is implemented as pure data/logic in `src/workflow/sandbox-platform-decision.ts` (`decideSandboxPlatformSupport`) -- no code in this Work Unit acts on the decision (no container is created); a future Work Unit's real CLI integration (WU38-04) is where a real `process.platform` value is first passed into this function from a live invocation.

## Rationale

Build spec Sec 5 ("Platform Strategy"): *"Valid initial outcomes include Linux container/runtime isolation, Linux namespace isolation, or another primitive with equivalent enforceable guarantees. Windows support must be explicit: supported through a real backend; supported only through WSL/container infrastructure; or unsupported initially. Unsupported hosts must fail closed and recommend request/import."*

This repository's own Node 24 CI (`.github/workflows/validate.yml`) runs exclusively on `ubuntu-latest` -- every job, every test shard, unconditionally. Choosing Linux as the initial supported platform means the platform this milestone can actually verify, in its own CI, on every push, is the platform it claims to support. Choosing "Windows, via Docker Desktop's internal Linux VM" or "macOS, via a container runtime" as an initial supported platform would be a guarantee this repository's CI cannot exercise at all -- exactly what build spec Sec 5's "must not claim cross-platform parity without equivalent guarantees" forbids. This decision is deliberately conservative, not a permanent architectural ceiling: `SandboxHostPlatformSchema` already reserves `darwin`/`win32`/`other` as distinct, first-class values (not folded into a single "unsupported" bucket), so a future milestone can add real Windows/macOS support as an explicit, separately-verified decision, without a schema migration.

## Platform/Backend Contract

| Property | Value |
|---|---|
| Supported OS | Linux only (initial). Verified exclusively via `ubuntu-latest` in `.github/workflows/validate.yml`. |
| Unsupported OS | macOS (`darwin`), Windows (`win32`), any other `process.platform` value. Each fails closed with an explicit, distinct reason string (`decideSandboxPlatformSupport`) -- never silently treated as "probably fine." |
| Host dependencies | An OCI-compatible container runtime (Docker Engine or Podman) reachable from the host running AIQT. No specific runtime is hard-selected by this Work Unit's contract -- `SandboxBackend.backendId`/`backendVersion` are runtime-reported strings, not a compile-time choice; WU38-02 makes the concrete runtime selection (and documents its own minimum version) when it implements the first real backend. |
| Minimum versions | Not yet pinned -- WU38-02 (the first Work Unit that actually shells out to a container runtime) is responsible for verifying and documenting the minimum Docker/Podman version this backend requires, since no such invocation exists in this Work Unit to test against a real version. |
| Isolation primitive | OCI container (Linux namespaces + cgroups, via the container runtime), matching `SandboxIsolationPrimitiveSchema`'s `"oci_container"` value. `"linux_namespace"` (a lower-level, runtime-independent namespace/cgroup implementation with no container-runtime dependency) remains a documented, schema-supported alternative for a future backend if the container-runtime dependency proves undesirable -- not chosen initially because an existing, widely-deployed container runtime gives WU38-02 a much smaller implementation surface than hand-rolling namespace/cgroup management. |
| Filesystem mechanism | Container bind mounts: one `read_write` mount for the run's own worktree, zero or more `read_only` mounts for approved runtime/tool paths, plus an isolated temp/output directory. No host home directory, no parent repository, no sibling worktree, and no arbitrary absolute path may ever be mounted (`SandboxFilesystemPolicySchema`, `validateSandboxFilesystemPolicy`). |
| Network mechanism | Container network namespace with `none` networking as the default (`SandboxNetworkPolicySchema.mode:"denied"`); an explicitly-approved run's network-enabled mode requires the backend to additionally report `network_destination_restriction` (a destination-allowlist-capable network configuration, e.g. an egress proxy or firewall rule set) before it may proceed at all -- a backend that can only offer "network on" with no destination control cannot support a network-enabled run, ever (build spec Sec 6). |
| Process control | The container runtime owns the sandboxed process's PID namespace, so process-tree ownership, graceful stop (`SIGTERM`), forced termination (`SIGKILL`/container kill), and orphan detection are all backed by the same real isolation boundary as the filesystem/network controls -- not a separate, weaker mechanism layered on top. |
| Resource control | Container cgroup limits: CPU shares/quota, memory limit, and (where the runtime supports it) block-IO/disk-write limits and a `pids` controller for process-count limiting. `SandboxResourcePolicySchema` is the data shape a real backend must translate into these cgroup settings. |
| Cleanup | Container removal (`docker rm`/equivalent) plus deletion of the isolated temp/output directory; `SandboxCleanupStatusSchema` requires the real outcome of that removal to be captured and reported, never assumed. |
| Unsupported-host behavior | `decideSandboxPlatformSupport` returns `supportStatus:"unsupported"`, `backendId:null`, `isolationPrimitive:"none"`, and a platform-specific `reason` string. No code path anywhere in this Work Unit (or the schema/contract it defines) has a branch that proceeds to sandbox creation on an unsupported platform -- `SandboxCreateRequest` requires a `SandboxFilesystemPolicy` etc. that only makes sense once a backend has already been selected, and `sandbox-fallback-policy.ts` is the only recommendation any unsupported-host caller can reach. |

## Why Not "Equivalent Guarantees" on Windows/macOS Yet

Docker Desktop on Windows/macOS does provide real Linux-namespace/cgroup isolation -- inside its own managed Linux VM. In principle this could satisfy "another primitive with equivalent enforceable guarantees" (build spec Sec 5). This Work Unit does not claim that equivalence for two concrete reasons, both fixable by a later, deliberate decision rather than an oversight:

1. **No CI verification.** This repository's CI never runs on a Windows or macOS runner with Docker Desktop installed. A guarantee this codebase's own test suite cannot exercise on every push is not one WU38-01 is willing to assert as "supported."
2. **Operator environment variance.** Docker Desktop's own isolation guarantees depend on configuration this project does not control (WSL2 backend vs. Hyper-V backend on Windows, resource limits the operator sets in Docker Desktop's own settings). A "supported" claim implies AIQT can enforce its documented policies regardless of that variance; verifying that is real, additional work, not automatic from "Docker Desktop exists."

If broader host support is desired later, the natural path is a dedicated Work Unit (or milestone) that adds Windows/macOS CI coverage first, then extends `decideSandboxPlatformSupport` to return `"supported"` for those platforms with its own documented host-dependency/minimum-version table -- not a change to this Work Unit's decision.

## Unsupported-Host Fail-Closed Behavior (Cross-Work-Unit Invariant)

Per build spec Sec 8 invariant 3 ("No silent unsandboxed fallback") and Sec 1.1 ("The request/import workflow is a permanent safe fallback"): any caller that receives `supportStatus:"unsupported"` from `decideSandboxPlatformSupport` must recommend `aiqt autonomous run` (the M37 request/import workflow) and must never attempt live execution by any other means, including a bare, unsandboxed process launch. `src/workflow/sandbox-fallback-policy.ts` is the single function that produces this recommendation; no other module in this Work Unit constructs one independently.
